## これはあくまで一例

TDD で辿り着く形は 1 つではありません。次のような点はペアの議論次第で別解になります。

- メソッド名（`Includes` / `Contains` / `Overlaps` など）
- 等価性の実現（`IEquatable` 実装 / `record` 化 / 値比較ヘルパ）
- 交差しない区間の共通部分（`null` / 空を表す専用の値 / 例外）
- コンストラクタで弾く例外の型（`ArgumentException` / `ArgumentOutOfRangeException` / 独自例外）

「正解と違うから駄目」ではなく、**テストで意図が表現できているか / 小さく進められたか**を見る。

## 想定する TDD の道すじ（一例）

1. `閉区間は下端点と上端点を持つ` — フィールドとコンストラクタだけ
2. `文字列表現を返す` — `ToString`
3. `下端点と上端点が等しい区間は作れる` — 実装は変わらないことが多い（仕様の確認テスト）
4. `下端点が上端点より大きい区間は作れない` — コンストラクタにガード追加
5. `整数が区間に含まれるかを判定する` — `Includes`
6. `区間どうしの等価性を判定する` — `Equals` / `GetHashCode`
7. `区間が別の区間を完全に含むかを判定する` — `Contains`
8. （発展）`交差するか` → `共通部分を求める`

各ステップで「次に何をテストするか」をペアに決めさせるのが主眼。順番は前後してよい。
