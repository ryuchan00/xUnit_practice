# AI 禁止のペアプロ TDD 研修（ひな形）

二人一組で、AI ツールを一切使わずに、TDD（テスト駆動開発）で小さなクラスを育てる研修の教材ひな形です。
お題は「整数の閉区間クラス（ClosedRange）」。

> この教材は、ペパボの新卒エンジニア研修
> [「AI時代のTDD」ワークショップ](https://tech.pepabo.com/2026/08/20/tdd-workshop-2026/)
> と、和田卓人さんの講演
> [「Agentic Software Engineering の時代における "テスト" と "TDD" の意味」](https://speakerdeck.com/twada/agentic-software-engineering-2026-07-findy-edition)
> を下敷きにしています。

---

## これは何をする研修か

- お題: 整数の閉区間 `[lower, upper]` を表すクラスを実装する（詳細は [`docs/お題-整数の閉区間.md`](docs/お題-整数の閉区間.md)）
- 形式: 2 人 1 組のペアプログラミング。ドライバー（キーボードを持ち、コードを書く人）と
  ナビゲーター（何をするか考え、指示・提案する人）を、こまめに交代する
- 道具: C# + xUnit。テスト実行は `dotnet test` だけ
- サイクル: Red → Green → Refactor を、1 サイクル 1 テストで小さく回す
- 時間の目安: 90〜120 分（下のタイムテーブル参照）

### 絶対ルール

AI コーディングツール（Copilot、Cursor、Claude Code、ChatGPT など）を一切使わない。
補完の類も含め、答えやコードを機械に出させない。ペアの頭と会話だけで進める。

---

## なぜ AI 禁止でやるのか

このお題は、AI に頼めば数十秒で完成します。それでもあえて手で書くのは、次のことに時間を使いたいからです。

### 1. 「理解」は外注できないから

> 思考は外注できるが、理解は外注できない。 — Andrej Karpathy（前掲スライドより）

AI は「動くコード」を先に出せます。しかし、その設計意図や境界条件を自分が理解しているかは別問題です。
理解しないままコードだけが積み上がる状態を、和田さんの講演では 認知負債（cognitive debt） と呼んでいます。
生成の速さに人間の理解が追いつかず、後から効いてくる負債です。

TDD は、この順序を意図的に元に戻します。
テストを先に書く = 何が正しいかを先に言葉にする。理解を先頭に置くための型です。

### 2. テストを書くことと、仕様を決めることは、ほぼ同じ営みだから

「`[3,8]` に 8 は含まれる？」「`[8,3]` を渡されたらどうなる？」——
テストを 1 本書こうとするたびに、こういう仕様の穴が見つかります。
ペアで「どうあるべきか」を決めてからテストにする。この繰り返しが、そのまま動く仕様書になります。

AI 時代にボトルネックになるのは、コードを書く速度ではなく「意図を明確にすること」と「検証」です。
その 2 つを、小さなお題で徹底的に練習します。

### 3. 小さいサイクルで、理解と出力を同期させる練習だから

1 サイクル 1 テスト。赤を見てから最小限で緑にする。緑のままリファクタする。
このリズムを体に入れておくと、AI と組んで速く進めるときも、
「今どこまで自分は分かっているか」を見失いにくくなります。

### 4. 人が集まらないとできないことに時間を使うため

研修の場は、講師と仲間が同じ部屋にいる貴重な時間です。
一人でも AI とでもできることは後でできる。
設計を声に出して議論する / 相手の考え方を観察する——ペアプロでしか得られないものに時間を割きます。

## 進め方（Red → Green → Refactor）

1. Red: 要件リストから 1 つ選び、それを確かめるテストを 1 本書く。ビルドは通るがテストは落ちる状態にする
2. Green: そのテストを通すためだけの、最小限の実装を `src` に書く
3. Refactor: テストが緑のまま、重複や名前の分かりにくさを直す
4. 1 に戻る。適当なタイミングでドライバー / ナビゲーターを交代する

- 要件リストの順番どおりにやらなくてよい。「次に何をテストするか」をペアで決めるのが練習
- 詰まったら、実装を書く前に「このテスト、そもそも何を保証したいんだっけ？」に戻る
- コミットは緑のたびに。メッセージに「何を仕様として決めたか」を書くと後で読み返せる

## タイムテーブル（目安・90〜120 分想定）

| 時間 | 内容 |
|---|---|
| 0:00–0:10 | イントロ。ルール確認（AI 禁止 / 1 サイクル 1 テスト / 交代）、ペア分け |
| 0:10–0:20 | お題の読み合わせ。`docs/お題-整数の閉区間.md` をペアで音読し、疑問を出す |
| 0:20–0:30 | 最初の Red → Green。`閉区間は下端点と上端点を持つ` を通す |
| 0:30–1:20 | 要件リストを進める。10〜15 分ごとにドライバー交代 |
| 1:20–1:35 | 発展課題（交差・共通部分）、または自分たちで要件を追加 |
| 1:35–1:50 | ふりかえり。下の問いをペア→全体で共有 |

---

## ふりかえりの問い

- テストを書こうとして初めて気づいた「仕様の穴」はどれ？
- AI に任せていたら、たぶん気づかなかったことは？
- 1 サイクルを小さく保てたか。大きくしすぎて赤の意味が分からなくなった場面は？
- ドライバーのとき / ナビゲーターのときで、考えていたことはどう違った？
- 「認知負債」を自分の言葉で説明すると？

## セットアップと実行

### .NET 10 SDK がある場合

```sh
cd pairpro-tdd-workshop
dotnet test
```

最初は `閉区間は下端点と上端点を持つ` が失敗し、残りは Skip 表示になります。そこがスタート地点です。

特定のテストだけ動かす:

```sh
dotnet test --filter "FullyQualifiedName~整数が区間に含まれるか"
```

### .NET SDK を入れたくない場合（Docker）

```sh
cd pairpro-tdd-workshop
docker compose run --rm tdd
```
