# Level 4: テストダブル

## この Level のいちばん大事な話

テストダブルは、極力使わないほうがよい道具です。

そのうえで、使えないと詰む場面が確実にあるので、道具として知っておく必要があります。この2つを両方持ち帰るのが、この Level の目的です。

## テストダブルとは

> テストダブル (Test Double) とは、ソフトウェアテストにおいて、テスト対象が依存しているコンポーネントを置き換える代用品のこと。ダブルは代役、影武者を意味する。

> テストを実行するには、被試験システムに加えて、テスト対象が依存するコンポーネント (DOC; Depend-On Component) が必要になる。しかし、依存コンポーネントは、常に利用できるとは限らない。依存コンポーネントがテスト環境で利用できない理由には、次のようなものが挙げられる[1]。

> - 入手できない。
> - テストで使いたい結果を返さない。
> - 実行に時間がかかるなどの、望ましくない副作用がある。
> こういった問題を回避するには、依存コンポーネントを、テスト用のコンポーネントと入れ替えるテクニックが利用できる。この代用のコンポーネントを、テストダブルと呼ぶ。

[Wikipediaより](https://ja.wikipedia.org/wiki/%E3%83%86%E3%82%B9%E3%83%88%E3%83%80%E3%83%96%E3%83%AB)

## 道具として必要な場面

「極力使わない」を「使ってはいけない」と受け取ると、テストできないコードだらけになります。ダブルが必須になるのは、だいたい次の場面です。

### 1. 外部APIを実際に叩かずに、呼び出し側のロジックを確かめたいとき

これが一番よく出てきます。`OrderService.PlaceOrder()` をテストしたいだけなのに、本物の `IPaymentGateway` を使えばテストを実行するたびに本当に課金され、本当にメールが飛びます。当然できません。

そこで決済APIをスタブに差し替え、

- 呼び出し側(`OrderService`)が通常どおり動くことを確かめる
- 外部APIについては「正しい引数で呼ばれたことだけ」を確認する(その先で何が起きるかは、外部サービスの責任であって、こちらのテストの関心事ではない)

という形にします。`StubExampleTests.cs`(呼び出し側が動くか)と `MockExampleTests.cs`(呼ばれたかどうか)の見本が、それぞれこの2つに対応しています。

### 2. 意図的に起こすのが難しい異常系を再現したいとき

決済APIが通信エラーを返す、タイムアウトする、DBが落ちる。本物相手にこれを毎回同じように起こすのは、ほぼ不可能です。

だからテストを書くのを諦める → 異常系だけテストが無い → 本番で初めて「例外を握りつぶしていた」と気づく、というのがよくある事故の形です。異常系のコードは本番でしか通らないまま放置されがちなので、ここにテストが無いのは効きます。

「起こせないからテストしない」ではなく「スタブで起こす」という選択肢を持っているかどうかが、そのまま品質の差になります。`StubExampleTests.cs` の3本目がこの課題です。

> ちなみに C# に `SystemError` という型はありません。近いものに `System.SystemException`(`NullReferenceException` などの基底クラス)がありますが、これは .NET 1.0 時代の名残で、Microsoft 自身が「継承するな・catch するな」と案内しているクラスです。実務で扱う異常系は `HttpRequestException`(通信失敗)や `TimeoutException` のような具体的な例外なので、この教材でもそちらを使います。

### 3. その他

- 時刻・乱数 — Level3B でやった `TimeProvider` がこれ
- 遅い処理 — 1回30秒かかる依存を、毎回のテストで待てない

## 覚えるのは3つでいい

| 種類 | 何をするものか | 使いどころ |
|---|---|---|
| スタブ (Stub) | 決まった戻り値を返す(例外を投げる場合も含む) | これが主力。異常系の再現もここ |
| モック (Mock) | 呼ばれ方を検証する。ダブル自身が `Verify()` で評価 | 「呼んだこと自体が結果」になる外部境界に限る |
| スパイ (Spy) | 呼び出しを記録するだけ。評価はテストコード側で行う | モックと同じ用途。何が起きたかを自分で確かめたいとき |

`DummyExampleTests.cs` と `FakeExampleTests.cs` の2つは、用語として知っておけば十分です。読んで意味が分かればよく、覚えようとしなくて構いません(ダミーは「渡すだけで使われない引数」、フェイクは「動く簡易実装」)。

## なぜ「極力使わない」のか

テストダブルを使うと、テストは「本物ではないもの」コードをテストすることになりグリーンになります。
本物との食い違いに気づけないです。スタブが返す `PaymentResult` は、あなたが「こう返るはずだ」と思っている形でしかありません。本物の仕様が変わっても、スタブは何も教えてくれず、テストはグリーンのままです。

なので、選択の優先順位は次のとおりです。上から順に検討し、無理なときだけ下に降りてください。

1. 本物をそのまま使う — 副作用も外部通信も無いなら、ダブルは要らない
2. 本物に近い簡易実装(フェイク)を使う — インメモリのリポジトリなど
3. スタブで戻り値だけ固定する — 戻り値さえ決まればテストが書けるなら、ここで止める
4. モック / スパイで呼ばれ方を検証する — 最後の手段

とくに 4 は、自分たちが所有していないプロセス境界(決済、メール送信、外部通知など「呼んだこと自体が結果になる」もの)に限るのが目安です。自分たちのコードの内部呼び出しをモックで固めるのは、たいてい後悔します。

## 進め方

1. `DummyExampleTests.cs` を読む。全体が見本で、書く作業はありません。「`stubPaymentGateway` は何をしているか」「なぜ `IReceiptPrinter` に `null!` を渡してよいのか」を説明できる状態にしてから次へ
2. `Stub` → `Mock` → `Spy` の順に、各ファイルの見本を読んでから Skip を外して書く。ここが本番です
3. `FakeExampleTests.cs` は最後に読む。時間があれば書く
4. プロダクションコード(`src/TrainingApp/`)は変更しない

## テストを書く前に毎回問うこと

- そもそもダブルは要るか? 本物で書けないか
- 要るとして、戻り値を決めたいのか(スタブ)、呼ばれ方を見たいのか(モック/スパイ)

## サンプルコード(スタブの例)

```csharp
[Fact]
public void GetPrice_為替レートAPIが1ドル150円を返すとき_日本円換算額を返す()
{
    // Arrange
    var stubExchangeRateApi = new Mock<IExchangeRateApi>();
    stubExchangeRateApi
        .Setup(api => api.GetUsdToJpyRate())
        .Returns(150m);
    var priceService = new PriceService(stubExchangeRateApi.Object);

    // Act
    var actual = priceService.ConvertToJpy(10m);

    // Assert
    Assert.Equal(1500m, actual);
}
```

## 発展課題

### 1. 決済ゲートウェイのスパイを手書きする

`SpyExampleTests.cs` に、`IPaymentGateway` を実装した手書きのスパイ(`SpyPaymentGateway`)を定義し、「注文したとき、どの金額・どのトークンで `Charge` が呼ばれたか」を記録して検証するテストを追加してください。

このとき `Charge` は `PaymentResult` を返す必要があります。記録するだけのスパイが、同時に決まった値も返していることになります。「これはスパイなのか、スタブなのか」を考えてみてください(現実のテストダブルは、しばしばこのように役割が混ざります)。

### 2. 同じ検証をモックとスパイの両方で書き比べる

`MockExampleTests.cs` の「注文するとき正しい金額とトークンで決済が呼び出される」と、上で書いたスパイ版を並べて見比べてください。

- 失敗したときのエラーメッセージは、どちらが読みやすいか
- プロダクションコードの引数が1つ増えたとき、修正が必要なのはどちらか

正解のある問いではありません。チームでどちらを選ぶかを議論するための材料です。

### 3. 「このモックは要らなかったのでは?」を探す

これまで書いたテストを見返し、ダブルを本物に戻せるものが無いかを確認してください。たとえば「呼ばれ方を検証していないのにモックを使っている」箇所は、より単純な書き方にできる可能性があります。使わずに済ませる判断ができて、この Level は修了です。
